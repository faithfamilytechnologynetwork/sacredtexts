## Defect 1 — the `expected` schema in Assumptions is wrong

The spec states `expected` "holds the **citation**; the gold text for a citation is resolved from the raw editions index, not from the answer row." Neither half holds. `expected` is **task-dependent**:

| task | `expected` keys |
|---|---|
| `cite_passage` | `citation` |
| `retrieve_quote` | `text` |
| `complete_unit` | `text`, `full_text` |
| `verify_source` | `answer`, `true_work`, `true_version`, `true_language`, `true_citation` |

On exactly the cells the counterfactual targets (`retrieve_quote` / `complete_unit`), `expected` carries **no citation at all** — the citation is in `question.source.citation`. And the gold wording *is* in the answer row (`expected.text`). A builder following Assumptions would key the `EditionIndex` off a nonexistent field. Fix: state that `source.citation` is the citation key (empty string on `verify_source`), `expected.text` is the gold wording, and the raw index is needed only for **sibling** editions' wording.

## Defect 2 — `complete_unit` in the counterfactual is undefined

Criterion 5 says "incorrect **text-retrieval** cells," and `outcomes.py::_TEXT_RETRIEVAL` = `("retrieve_quote", "complete_unit")`. But `complete_unit`'s gold is a *partial* unit (`expected.text` is the continuation; `full_text` is the whole verse). "The sibling edition's wording of the same citation" has no well-defined meaning for a partial unit — you'd need to reproduce the same split point in differently-worded text. Scope it to `retrieve_quote` only and say so, or specify the segment derivation. The split is material: of the 53 incorrect Bible text-retrieval cells, **32 are `retrieve_quote` and 21 are `complete_unit`**.

- **Restricted-index guard: right mitigation, wrong reason.** The spec credits "restricted texts are already excluded from the pool" — a different gate. State the `license != restricted` filter explicitly and test that a restricted target never enters the index even when present.
- **Join mechanics worth stating.** `selected_texts` entries carry only `{work, version, language}` — tradition/document_type/license come from the catalogue or `question.source`. And `scores.jsonl` rows carry no text identity, so any per-text breakdown requires joining to `answers.jsonl` on `(question_id, model_id)`.
- **Sub-metrics claim is task-scoped.** `exact/normalized/token_f1/contains_reference` exist only on text-retrieval rows; `cite_passage` has `{correct, n_candidates, outcome}` and `verify_source` has `{parsed, expected, correct, outcome}`. Card code must not assume them.

The ambiguity only bites if the card joins a *standardized* encyclical doc back to a target.
