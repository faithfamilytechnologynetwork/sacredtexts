### Issues

**1. Card prose lives in two places, not one (phase deliverable).** `_COUNTERFACTUAL_SCOPE` (facct.py:34) is card prose — it is rendered verbatim onto `facct.md` as `*Scope: …*` — but it sits at the top of the module next to the counting logic, not in `CARD_PROSE`. The phase's stated deliverable is "All prose lives in one constants block". Jonathan revising the card's wording would have to find this sentence in the analysis section. Move it into `CARD_PROSE` and have `_counterfactual` read it from there (the JSON `scope` field can keep pointing at the same constant).

**2. Typed numbers inside the prose block.** `counterfactual_intro` says "**Three** of the texts are different English editions of the same Bible (KJV, ASV 1901, WEB)", `non_conclusions` repeats "the **three** English Bibles", and `_COUNTERFACTUAL_SCOPE` says "the three English Bibles are the only sibling editions in the pool". The spec is absolute here: "no figure is ever typed into the prose, so the card cannot drift from the run." These are correct today but are exactly the drift surface the spec names — add a fourth public-domain English Bible to the catalogue and the counterfactual changes while the prose keeps saying "three". `census["selected_texts"]` already carries the Bible versions in the pool; interpolating the count and version list is a couple of lines and closes the gap.

**3. The human card never names the 17 texts.** `facct.md` shows only aggregate counts (`open 4 / public-domain 13`), so a reader cannot answer the question the spec's problem statement opens with — "which license governs each slice". The spec criterion reads "The census table covers all 17 selected texts by tradition, language, document type, and license"; `facct.json` satisfies it, `facct.md` does not. The data is already in `census["selected_texts"]` — a 17-row table (work/version, language, tradition, type, license) is a direct render.

**4. The composite census table is a readability hazard.** The three-breakdowns-side-by-side layout with spacer columns renders rows like `| ar | 10 | | hadith_collection | 9 | | open | 4 |`, which invites a non-engineer to read "Arabic = 10 texts, of which 9 are hadith collections, 4 open" — a relationship that does not exist. Three small separate tables cost nothing and remove the misreading.

**5. The four task names are never glossed.** `retrieve_quote` / `complete_unit` / `cite_passage` / `verify_source` appear as table rows, and the counterfactual column header reads "Of incorrect Bible retrieve_quote", with no explanation anywhere on the card. For a FAccT reviewer who has not read the pipeline, this is jargon. One prose line per task in `CARD_PROSE` fixes it and is squarely within "non-engineer readable".

### Minor (optional)

- `cli.facct` writes `facct.json`, then `facct.md`, non-atomically. A failure between the two leaves a fresh JSON beside a stale MD — the exact hazard `edition_index.write_export` already guards with a tmp+`os.replace` swap. Consider the same staging for consistency.
- `_within` accepts the run directory itself (`run_dir != resolved` is false ⇒ no raise), so `--md .` passes validation and then dies with an `IsADirectoryError` traceback instead of a `BadParameter`. One-line guard.
- The drift-guard test asserts one figure (retrieve_quote accuracy). The rendered census counts and counterfactual numerator/denominator are not tied back to the data by any test. A stronger guard — assert each number appearing in the rendered tables is present in the report structure — would cover the whole card rather than one cell.

None of these are counting bugs; the numbers are right and the integrity checks behind them are good. I'm asking for changes because Phase 4 commits this Markdown into the repo as the paper-facing artifact, so items 1–3 are much cheaper to fix now than after the card is generated and reviewed by Jonathan.
