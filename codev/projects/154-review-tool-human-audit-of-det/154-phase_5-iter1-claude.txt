## The blocker

The phase-5 acceptance criterion "`pnpm -C apps/viewer test` passes" is **currently red**:

```
❯ src/lib/reviewStore.test.ts (37 tests | 2 failed)
  × A's save conflict that lands after B signs in neither retries nor adopts A's draft
  × a save still queued when the session resets never runs
    → expected [ 'b PUT /api/review/S' ] to deeply equal [ 'a PUT /api/review/S' ]
 Tests  2 failed | 353 passed (355)
```

Two isolated reruns of that file alone: `37 passed`, `37 passed`. So this is **order-dependent flakiness in the new tests, not a store bug**.

Diagnosis, by reading (I did not mutate the tree): `twoAccounts()` flips `who = "b"` when the login *request* is handled, whereas the store's `session` only bumps once the login *response* is consumed. The enqueued PUT is issued in a microtask whose interleaving with the login promise chain is unpinned, so the single PUT sometimes gets tagged `b` by the fake. Note the substantive invariant — **exactly one** PUT, no LWW retry, no second queued save — held in both the passing and the failing runs. The epoch logic is right; the assertion is reading the fake's caller tag, which isn't deterministic.

Suggested fix: park the PUT in flight deterministically before switching accounts (drain to a macrotask), then assert the PUT *count* and the absence of A's state/version rather than the fake's caller attribution.
