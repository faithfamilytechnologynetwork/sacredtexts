### Issue 1 (blocking): the committed sample is a new restricted-text artifact outside the copyright gate

`texts/raw/Protestant Christian/source.yaml` marks **NRSV `license: restricted`**, and `audit.py` gives it a 500-verse quotation allowance keyed on `(work, version, language)` + a per-row `source.citation`. The committed-artifact test (`test_audit.py:33`) scans only `git ls-files runs/`. The plan commits a ~3 MB `review/samples/*.json` containing NRSV `expected.text` and answers — a **new committed artifact derived from a restricted source that nothing audits**. `arch-critical.md` states the invariant flatly: "no committed artifact may derive from a `restricted` source."

Worse, if you simply point the audit at it, it fails: `_iter_source_dicts` only looks at top-level `source` / `question.source`, so the plan's nested `cells[].source` is **invisible to the origin layer** ⇒ `quoted` stays empty ⇒ the content layer scans the blob and flags "contains restricted text" for any developer who holds the NRSV payload locally (green in CI, red on the owner's machine).

Phase 1 should add: (a) teach `_iter_source_dicts` the sample shape (`cells[].source`) so the quotation allowance applies, (b) extend the committed-artifact audit test to `git ls-files review/`, and (c) an acceptance criterion that the committed sample passes the audit **with restricted payloads present**, plus a distinct-NRSV-citation count (~110 cells, far under 500 — but assert it).

### Issue 2 (blocking, small): Phase 4 rebuilds a static host that already exists in-repo

`apps/viewer/server/index.mjs` is already a Hono static host doing exactly `serveStatic({root: DIST})` + `notFound → index.html`, pinned by a **real smoke test** in `src/deploy.test.ts` (spawns `pnpm start`, asserts deep-link fallback and a real JS asset content-type). `apps/viewer/railway.json` already exists. Phase 4 says `static.ts` is "adapted from multibench's edge static half" and adds a second `railway.json`, without mentioning either in-repo artifact. Per `lessons-critical` ("check for existing work"), Phase 4 should port the in-repo host and state what happens to `apps/viewer/railway.json` / `pnpm start` (kept for the Pages-independent static host? retired?) so there aren't two un-reconciled deploy configs claiming to serve the viewer.

Related, and worth one line in the plan: the Railway build is `pnpm -C apps/viewer build`, **not `build:pages`**, so the review host ships the viewer with no baked runs — `/`, `/errors`, `/standings` will show "no runs" there (README line 126 describes this exact behaviour under `wrangler dev`). That's acceptable for a review-only origin, but it should be stated, not discovered.

### Issue 3 (blocking, small): a 413 on the ported store retries forever

Worst case is ~1,423 labels × 1,000-char notes ≈ 1.4–1.5 MB against a 2 MB cap — thin headroom, and `review.ts` (multibench) schedules a **retry timer on any failed save**, keyed per draft. A 413 is permanent: the reviewer would get a silent save-retry loop with no path forward. Phase 5 should add a deliverable: a 413 (and any 4xx that isn't 409/403-CSRF/401) is a terminal, visibly-surfaced failure with no retry, plus a regression test. Consider also a client-side byte guard before PUT, or a 4 MB cap.
