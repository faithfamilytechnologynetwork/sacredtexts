## Must fix

**1. The draft rubric (OQ1) contradicts Spec 48's assertion gate, so the headline number would partly measure a definitional mismatch, not scorer error.**

Spec 48 is explicit (lines 121–128): a **class A** answer — "I couldn't find the exact edition, but from memory it is: …" followed by the delivered passage — is *scored on its merits, not refused*. Only **class B** (declined with a substitute/pointer/nothing) stays `refused`. The draft rubric says retrieve_quote is "**Refused** if it declines or says it can't provide the text … even when it offers a summary or translation instead." A reviewer following that text marks class A as `refused`; the scorer marks it `correct`/`incorrect`. That band is not small — retrieve_quote has 1,834 `refused` and Spec 48 found this class dominating its 100-cell survey. The result is a manufactured false-negative signal that no scoring change could fix.

Same shape for *verify_source*: the scorer takes the **leading-stance** verdict within the first sentence / 60 chars (arch-critical, #23). The rubric's "correct if its committed yes/no matches … refused if it never commits" reads as *final* stance, so "This cannot be verified… No." splits human from scorer by definition.

Fix: state the assertion test in the reviewer's words ("did the answer present the passage *as its answer*, however hedged?") and the leading-stance rule for verify_source — or declare the divergence intentional and require the report to separate "definitional divergence" from "scorer error". Either way the spec should name Spec 48 and #23 in OQ1 so the architect settles it knowingly.

**2. "The committed set passes `audit.py` in the test gate" is unsatisfiable as written, and the set's location is unspecified.**

`pipelines/tests/test_audit.py::test_committed_run_evidence_is_clean` audits `git ls-files runs/` only (lines 36–40). The spec requires the set be committed "outside existing run evidence" but never names a path. A new top-level dir would be audited by **nothing** — and would also match no prefix in `.codev/checks/test.sh`'s `grep -oE '^(apps/[^/]+|pipelines|items|runs|texts|configs|CODE_WALKTHROUGH\.md)'`, so a review-set-only change runs **zero tests**. That is precisely the dispatcher blind spot `lessons-critical` records (the `fixtures/` gap closed by PR #44, Spec 48's viewer break as the proof case).

Two clean options: put the set under `runs/<set-id>/` (inherits the audit scan and the pipelines+viewer lanes for free — but verify the viewer's run discovery/`bake-runs.ts` doesn't surface it as a broken run), or pick a new top-level dir **and** add success criteria for extending `test_audit.py`'s committed scan and the dispatcher registry. The spec names only `apps/api` registration today.

**3. Account delete vs. research-record integrity is undecided.**

"Account delete cascades to the reviewer's sessions, assignments, drafts and submissions" collides with "the paper can cite these numbers". A reviewer deleting their account after an export silently invalidates published figures, and the pseudonym can no longer be traced for errata. Decide in the spec: anonymize-and-retain judgements (delete only identity), or hard-delete with the consequence stated in the signup consent text, or block deletion after an export is published. This is a WHAT-level policy question with ethical weight — it shouldn't be found during implementation.

## Worth considering (non-blocking)

- **Power, not just allocation (OQ4).** ~2,000 cells across outcome × task × tradition (×grader path) is ~100–130 strata, ~15 cells each — per-stratum Wilson intervals around ±25pp, uninformative. And with a handful of reviewers the *judged* count may be 200–500, not 2,000. Give OQ4 a target precision ("aggregate FP rate to ±5pp needs ~400 judged `correct` cells") so the architect can answer it arithmetically, and say which breakdowns are expected to be citable vs. descriptive.
- **#41 adjudication has no success criterion.** The spec says this tool "is the vehicle for that adjudication", but nothing covers resolving an overlap disagreement (third rater, tie-break, adjudicator role). Either add a criterion or scope it out explicitly.
- **Question-defect flag's effect on the denominator** is unspecified — is a flagged-but-judged cell in the agreement rate, or in its own bucket like `can't judge`?
- **Claim-race concurrency.** Claim-based assignment needs a documented behaviour (and test) for two reviewers claiming the same cell concurrently. The test list covers "non-overlap cells reach one reviewer" but not the race — and this repo's port source has a race-safe-signup fix for the same class of bug.
- Scope is large for one spec (Python sampler + stats, a new `apps/api`, viewer routes, export, deploy runbook, committed set). The port de-risks it, but naming an MVP cut — say, set builder + report + local-only service first, hosting second — would help the plan phase gate honestly.
