## Blocking issue: a committed verdict plus a caveat is scored `refused` (and zeroed)

`_with_outcome` (`score.py:305`) applies verify_source refusal **ungated**:

```python
refused = classify_refusal(...) and (task == "verify_source" or not metrics["correct"])
```

That ungating was correct under Spec 15, whose rationale is stated inline: *"so an incidental Yes/No token in the decline cannot score correct"* — because the old parser matched yes/no **anywhere**. Phase 3 removes that premise. A parse result is now, by construction, a *leading* verdict. The ungating therefore now discards real verdicts. Verified against the actual code:

```
'No, I cannot verify that this is from the King James Version.'
  → {'parsed': 'no', 'expected': 'no', 'correct': 0, 'outcome': 'refused'}
```

The model gave the exactly-right false-premise answer; it is zeroed and dropped from the accuracy denominator. This is not hypothetical phrasing — "No, I can't confirm this appears in…" is a very plausible shape for the search-on arms, and verify_source is the benchmark's false-premise instrument.

It also contradicts the codebase's own two statements of intent:
- `outcomes.classify_refusal` docstring (`outcomes.py:107`): *"verify_source : leading decline cue **AND no Yes/No was committed**"* — which the code does not implement.
- `test_outcomes.py:70-71`: *"a leading decline that still commits a Yes/No is an answer, not a refusal."* That test passes **vacuously** — `"I can't be fully sure, but yes."` contains no cue from `_DECLINE_CUES_RAW` (it's a hedge), so `leading_decline` is `False` for reasons unrelated to the committed verdict. Substitute a real cue (`"I can't verify that, but no."`) and it fails.

Requested change (small, and it must land before Phase 6 — fixing it after the run is committed becomes a sanctioned rebaseline):

```python
if task == "verify_source":
    refused = classify_refusal(answer, task, expected) and metrics["parsed"] is None
else:
    refused = classify_refusal(answer, task, expected) and not metrics["correct"]
```

plus tests pinning `"No, I cannot verify that this is from X."` → `correct=1 / outcome=correct` and `"I can't verify this."` → `refused`, and de-vacuuming `test_outcomes.py:71`.

## Non-blocking, but needs architect visibility

1. **Strict leading-token is narrower than the spec's "first sentence / first 60 chars."** I think the tightening is defensible — a window search would match the incidental `no` in *"There is no way to verify this"* (that phrase is **not** in `_DECLINE_CUES_RAW`, which is first-person only, so the decline layer would not have saved it), and false-*correct* on an evasion is strictly worse than false-incorrect. But the cost is real and measured:

   ```
   'Based on my search, yes - this is Sahih al-Bukhari 1.' → None → incorrect
   'Answer: Yes'                                           → None → incorrect
   ```
   A committed verdict in a non-leading form is scored **wrong**, not excluded. The spec's own risk row says "use first-sentence/first-60-chars as specified," so this is a deliberate deviation that should be surfaced, and Phase 6 should include a pre-commit diagnostic: count verify_source rows with `parsed is None` and no decline cue, and eyeball them **before** committing the run.
