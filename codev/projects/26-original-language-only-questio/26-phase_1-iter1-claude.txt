## Blocking finding: the metadata channel cannot key the encyclicals

`convert_encyclicals` (convert.py:229–239) emits one `Document` per file with `work=title` and `version=f"Vatican English text ({pope}, {date})"` — **not** the target's nominal `("Papal Encyclicals", "Vatican English", "en")`. The RC `source.yaml` says so itself at lines 6–8. So:

- `text_metadata()` produces a key for `("Papal Encyclicals", "Vatican English", "en")` that matches **zero** standardized documents.
- Every one of the ~201 encyclical documents has a tuple absent from the map → `metadata_for_text()` raises `CatalogueError` by design.

This is not only the `--include-translations` path. Phase 2's selection predicate needs `canonical_language` to *decide* inclusion, so the lookup must happen before the encyclicals can be excluded. The normal invocation generates over the whole standardized tree (the committed first-run manifest's `inputs` literally lists `texts/standardized/Roman Catholic/papal-encyclicals-vatican-english-en`), so **the default path hits the fail-closed raise too**. Separately, under one-text-per-`(work, version, language)` grouping the encyclicals become ~201 "texts" of a few paragraphs each, which can't fill a 28-question quota regardless.

I'm not asking you to implement the Phase-2 selection fix here. I am asking that the Phase-1 contract not ship asserting a guarantee it can't deliver: either the map needs a second keying route for converters that re-stamp work/version, or the encyclicals need an explicit, tested exclusion — and that's an architect decision (it changes what `--include-translations` means in the spec). Worth a `afx send architect` now rather than discovering it mid-Phase-2.

## Secondary: `text_metadata()` is fail-open across source files

```python
for t in all_targets(sources):
    meta[t.text_key] = TextMeta(...)   # last writer wins, silently
```

The docstring claims "Targets that share this tuple have already been forced to agree on both fields by `load_source`'s slug-agreement check." That's true *within one `source.yaml`* only — `load_source` runs per file, and `discover_catalogue` never cross-checks. Two files declaring the same `(work, version, language)` with different `requested_as` would silently resolve by glob order. No collision exists in today's catalogue, so impact is zero now — but it's a fail-open in a channel whose whole design point is fail-closed, and it's a ~5-line fix (raise on a conflicting duplicate in `text_metadata`, plus a test). The docstring claim should be corrected either way.
