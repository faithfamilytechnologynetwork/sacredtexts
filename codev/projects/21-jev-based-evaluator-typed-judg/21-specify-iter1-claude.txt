## Issues

**1. What the `graders.py` registration actually *means* is unspecified — the main clarity gap.** Success criterion 1 requires registering `jev` in `GRADERS`, which implies declaring `metric_keys`. But the module docstring promises those keys are "merged into each row's open metrics map by a later pass," and Approach 1 explicitly does **not** merge — it writes a sidecar whose fields are `refusal_p`, `matches_requested_p`, `kind`, `kind_probabilities`, `kind_confidence`. So as written, `jev`'s declared `metric_keys` would name fields nothing ever writes. (Also worth knowing: `submetrics_for` filters through `_CANONICAL_ORDER`, so such keys would be silently dropped if they ever did reach it.) State either (a) the exact `metric_keys` and that Part 2 records them *in the sidecar* under those names, or (b) that registration is selection/discovery-only and the merge is explicitly deferred.

**2. Under Open Question (a), the title and Desired State overstate what ships.** The spec is titled "containment **and passage equivalence**," but option (a) leaves `other_indexed_wording` unable to fire — passage equivalence degrades to requested/neither. No success criterion covers the equivalence label, so the spec can be "fully satisfied" without delivering half of its stated purpose. Add an explicit fallback criterion: with empty alternates, `kind ∈ {refusal, requested_wording, neither}` and `other_indexed_wording` coverage is deferred to the cross-translation part — and retitle or caveat accordingly.

**3. Spend precedent is factually wrong.** "Surfaced the way `collect`'s is" — `collect` surfaces nothing; it records per-row `usage`. The cost table is built in **`score.py:617-639` and rendered at :780-793**, and only from `configs/models.yaml` `price_in`/`price_out` (runs without prices are UNPRICED). Jev is different in kind: the Decisions API *returns* `usage.cost` per call. Say so, or a builder will go looking for a pricing hook that doesn't apply.

**4. `jev-latest` is a floating alias used as the resume key.** `_existing` keys on `(question_id, model_id, judge_model)` where `judge_model` is the *requested* id. If the build rolls 1.14 → 1.15 between passes, resumption silently mixes builds in one judgments file and in one agreement report. The resolved build is recorded per cell and `summarize` already collects `judge_models` as a set — add a criterion that a multi-build file is flagged (warn or fail), and consider allowing a pinned build.

**5. Restricted-text *transmission* is unaddressed (security/licensing).** Every criterion is about *committed artifacts*; `audit.py` enforces origin + content on commits. But judging sends `requested_text` — the expected reference — to a third party. I checked: neither committed run contains a restricted source (original run is BoM/D&C/PoGP, sunnah.com Arabic, WEB/ASV/KJV, Davidson Talmud, Uthmani QUL), so this is latent, not present. One constraint line would close it: the pass refuses or warns on cells whose `(work, version, language)` maps to a `restricted` catalogue target.

**6. The $8 cap is an instruction with no mechanism.** Per-call cost is only known *after* the call. Cheap fix worth a criterion: a pre-flight "N pending cells × ~$3e-5 ≈ $X" line plus a `--limit`, so the cap is enforceable rather than aspirational.

**7. One open question is mis-prioritized.** The refusal-probability threshold is filed "Nice-to-know," but you cannot produce the required agreement table without it. Promote it, or define the agreement report to tabulate the raw probability distribution per outcome class and avoid a threshold entirely.

**8. Suggestion, aligned with your own lesson.** `lessons-critical.md` says mocking the provider seam hides live-only failures. Commit the live-verified response (redacted) as the fixture `interpret()` is tested against, so the fail-fast tests are pinned to the real shape rather than a hand-written mock.

None of these require a redesign. (1) and (2) are the two I'd want fixed before planning; (3)–(7) are one-or-two-line additions.
