### Blocking issue: the dagger→alef rule makes the dagger diacritic load-bearing, and un-credits perfect answers

`fold_arabic_orthography` promotes U+0670 (category Mn) to the **letter** ا. But `strip_script_marks` documents the opposite contract — *"applied to BOTH the answer and the expected text, so the direction of vocalisation does not matter."* Applying the fold to both sides is **not** the same as being insensitive to whether a side *carries* the mark. Measured on the corpus:

```
corpus words containing U+0670:                                   2648
  of those, score_normalize(w) != score_normalize(w minus dagger): 2276
  (today: normalize(w) == normalize(w minus dagger) for all 2648)
```

So for 2,276 word-forms, an answer that reproduces the consonantal skeleton **without** the Uthmani dagger — the overwhelmingly common model output style — stops matching. This is not theoretical. On the committed tutorial run:

```
tutorial-2026-10-11   arabic retrieval cells=132   gained=20   LOST=2
  haiku / retrieve_quote-07ca676a80ab   committed: normalized=1 contains_reference=1 correct=1
  haiku / retrieve_quote-5c645a8301ad   committed: normalized=1 contains_reference=1 correct=1
```

Both are answers where `normalize(answer) == normalize(expected)` **exactly** — perfect retrievals. Under the fold both go to `normalized=0, contains_reference=0, correct=0`. The sole diff is an alef the fold *inserted into the expected text*:

```
expected new: ... ان كنت من الصادقين      (ٱلصَّٰدِقِينَ → dagger became ا)
answer   new: ... ان كنت من الصدقين       (model omitted the dagger)
```

A benchmark whose stated purpose is "don't penalise a content-correct answer for presentation" would, after this change, mark two verbatim-correct Qur'an retrievals wrong. That's the spec's own harm, inverted.

**Root cause, and why it's the same class the spec already ruled on.** The dagger spells long ā, but standard Imla'i *also* omits the alef for the defective-spelling (رسم ناقص) class — `هذا`, `ذلك`, `الله`, `الرحمن`, `لكن`, `أولئك`, `إله` — while writing it for `الكتاب`, `سبحان`, `الصادقين`. Verified:

```
ذَٰلِكَ      vs ذلك      old=1 new=0   (ذالك vs ذلك)      <== LOST
هَٰذَا       vs هذا      old=1 new=0   (هاذا vs هذا)      <== LOST
ٱلرَّحْمَٰنِ vs الرحمن   old=1 new=0   (الرحمان vs الرحمن) <== LOST
ٱلْكِتَٰبِ   vs الكتاب   old=0 new=1   gained
سُبْحَٰنَ    vs سبحان    old=0 new=1   gained
```

A context-free `dagger → ا` is wrong in exactly the way the spec proved a context-free `ىٰ → ا` is wrong — and here the split is **lexical, not positional**, so no position predicate fixes it. The medial-digraph rule inherits the same defect (`أَتَىٰكُمْ`→`اتاكم` but `أَتَىكُمْ`→`اتيكم`).

The direction I'd suggest exploring: make the long-ā alef **optional in the containment predicate** (where the whitespace-flex machinery already lives) while leaving `normalized` on today's dagger deletion. Since the default headline is `normalized OR contains_reference`, that is a strict superset — it keeps all 35 gains and loses nothing. I sketched this but did **not** get a working implementation, so treat it as a direction, not a validated fix. Options to weigh with the architect: this, versus accepting and pre-registering the losses (contradicts SC "credits every content-correct cell that can be credited"), versus narrowing the dagger rule.

Be aware the split direction isn't uniformly harmful — of 137 fold-induced splits, some are genuine *disambiguations* (`أَبْصَـٰرُ` "sights" vs `أَبْصَرَ` "he saw" are correctly separated). This needs judgment, not a blanket revert.
