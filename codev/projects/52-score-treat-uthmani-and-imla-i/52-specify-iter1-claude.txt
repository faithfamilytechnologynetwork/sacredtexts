## Blocking issues

**1. The enumerated rule set cannot jointly satisfy Success Criterion 1 and the non-collision scenario. The ا/ى/ي relation is context-dependent.**

I implemented the spec's own list (digraph `ىٰ`→ا, then bare ى→ي, wasla→ا, ء dropped) and ran it:

```
عَلَىٰ → علا   vs  على → علي     NOT equal
```

`ىٰ` must fold to **ا** for أَتَىٰكُمْ↔أَتَاكُمْ (the spec's residual-cell rule) but to **ى/ي** for عَلَىٰ↔على — one of the most frequent words in the corpus. No context-free character mapping satisfies both. The only context-free fold that *does* satisfy all four enumerated pairs is collapsing {ا, ى, ي, ـٰ, ٱ} into one class, and that provably merges distinct words:

```
قَالَ ≡ قِيلَ    بَيْت ≡ بَات    سَأَلَ ≡ سَالَ
```

A position-aware digraph rule (medial `ىٰ`→ا, word-final → ي) fixes عَلَىٰ and ٱلصَّـٰبِرِينَ and avoids those collisions — I confirmed that direction works — but it is *not* what the spec enumerates. Please either state that the fold must be position/context-aware, or demote the Assumption ("a fold covering all listed pairs resolves every cell") to an Open Question.

Relatedly, the collision Open Question is scoped too narrowly: it asks whether two distinct *benchmark units* collapse. But `contains_reference` is substring and `token_f1` is token-based, so a **word-level** merge credits a wrong word inside an otherwise-correct answer — and the projection oracle won't catch it, since it only pins Arabic flips to a registered set. Widen the non-collision criterion to word level against corpus vocabulary.

**2. Word segmentation is an omitted fold dimension, and SC-2 is unreachable without it.**

The spec's headline example (يَـٰبُنَىَّ ↔ يَا بُنَيَّ) is a *word-boundary* difference. It does not fold equal under any character rule — only with whitespace removed, which is exactly what the experiment's working fold did ("whitespace removed; containment match", run README:71). Measured on the 14 ar `retrieve_quote` cells under the most permissive character fold:

```
containment, whitespace stripped: 10/14
containment, whitespace kept    :  8/14
```

The pair list and success criteria never mention it, so a builder implementing only the enumerated pairs misses 2 cells and cannot hit "credits every content-correct cell."

This has a contract consequence the spec must decide: if Arabic whitespace is stripped inside `normalize()`, Arabic `token_f1` degenerates to a single token and `exact`/`normalized` change meaning for Arabic. Spec 15 requires text-retrieval to report all four submetrics — say what happens to them.
