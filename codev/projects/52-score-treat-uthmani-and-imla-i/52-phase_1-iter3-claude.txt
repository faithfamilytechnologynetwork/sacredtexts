## Findings

**1. `_fold_containment_pattern` emits an unmatchable literal `\n`/`\t` — the fold branch is permanently dead for multi-line references.** The builder mirrors `normalize()`'s punctuation and casefold passes but not its final `_WS_RE.sub(" ", …)` collapse. A `\n` is neither punctuation (`[^\w\s]`) nor `" "`, so it survives as `re.escape("\n")` → a required literal newline, while the answer side (`score_normalize`) has already collapsed all whitespace to single spaces. Verified:

```
ref "ٱلْكِتَٰبِ\nسُبْحَٰنَ" vs ans "قال الكتاب سبحان ربنا"  → bounded False, fold False
ref with " " instead of "\n"                              → fold True
```

This is not hypothetical: **23 Arabic `retrieve_quote` references in `original-2026-10-21` contain `\n`/`\t`** in `expected["text"]` (hadith chains — `retrieve_quote-094539b57f83`, `-131479631da4`, …). Those references can never take the fold branch.
